2.1 Analyze algorithms for correctness
An algorithm is considered correct if its output matches the expected results for
a given input. Analyzing an algorithm for correctness involves demonstrating
that it consistently produces the intended output for all valid inputs.
Two commonly used and effective methods for this analysis are:
Trace Tables
Stepwise Reasoning
2.1.1 Trace Tables
★ GOLDEN TOPIC
A trace table is a technique used to monitor how the values of variables change
during the execution of an algorithm. It is essentially a "paper execution" of the
code, often referred to as a manual walkthrough or dry running.
Purpose of Trace Tables:
Dry Running: Manually acting as the computer to execute the algorithm
line by line.
Debugging: Identifying logical errors where an algorithm runs but
produces incorrect outputs.
Validation: Ensuring the algorithm does what it is intended to do.
Components of a Trace Table:
Line Number: The line of algorithm being executed.
Variables: A column for every variable.
Input/Output: A column(s) for user inputs and printed output.
Condition Check: A space to evaluate conditions (IF, WHILE, FOR, etc.).

2.1.2 Stepwise Reasoning
Stepwise reasoning involves breaking an algorithm into logical sections and
verifying the "state" of the algorithm at each stage. It is also known as logic
verification.
This method checks correctness by carefully thinking through the logic rather
than using a detailed table row-by-row. The steps are:
1. Analyze each step of the algorithm.
2. Check:
Does the algorithm start in a valid state?
Does it handle all possible cases?
Are the conditions correct?
If the loop is correct at the start of an iteration, does it remain correct at the
end?
Example: Sum of N Numbers
The following algorithm calculates the sum of numbers from 1 to N. Where N is an integer
input number entered by the user.
Step 1: Start
Step 2: Input N
Step 3: SET Sum = 0
Step 4: For i = 1 to N
Step 5:   Sum = Sum + i
Step 6: END For
Step 7: Print Sum
Step 8: End
Stepwise Reasoning Breakdown:
Initial State: Initially, Sum = 0. This is valid.
Loop Boundary: Loop runs exactly from 1 to
N.
Iteration: Each number is mathematically
added to Sum.
Final State: After loop ends, Sum correctly
holds total.
Edge Case: If N=0, the loop does not run,
and Sum remains 0 (Correct). If N=5, Sum
becomes 15 (Correct).

2.2 Evaluating the Clarity of an Algorithm
Clarity in an algorithm means it is easy to read, understand, and modify. In
many cases, evaluating clarity is even more important than optimizing for
speed. A clear algorithm is easier to maintain, debug, and extend over time.
The two key aspects of clarity are:
Modularity
Readability
2.2.1 Modularity
Modularity means breaking an algorithm into smaller, independent parts such
as functions, classes, or modules. This makes the algorithm more organized and
easier to work with.
How to Evaluate Modularity:
1. Single Responsibility Principle (SRP): The SRP suggests that each module should
focus on one specific task. If a function is handling multiple tasks, it violates
modularity.
2. Coupling: Modules should be designed so they can be reused easily in different
contexts. Good modularity means loose coupling, where changes in one part do
not negatively affect others.
3. Abstraction: A well-designed algorithm hides complex implementation details. For
example, a user can call a sorting function without needing to know whether it uses
Bubble Sort or Selection Sort internally.

##P30
2.2.2 Readability
Readability refers to how easily another person can understand the purpose
and logic of an algorithm without actually running it. It is about how clear the
text and flow are.
How to evaluate readability:
1. Naming conventions: Rules for naming variables in a consistent way. Good
naming makes an algorithm easier to search and understand.
✗ Bad: v = d / t
✓ Good: velocity = distance / time
2. Self-documentation: An algorithm should be written clearly enough to explain
itself, reducing the need for excessive comments. Using meaningful names and
clean formatting helps make the purpose obvious.
3. Control flow simplicity: The logic should be straightforward. Avoid deep nesting
(e.g., IF inside IF inside IF), limit unnecessary conditions, and keep functions focused
on a single task.
4. Consistency: Following a standard style throughout the algorithm, such as
consistent indentation, spacing, and casing (like camelCase or snake_case),
allows the logic to stand out clearly.

2.3 Assess Algorithm Efficiency
★ GOLDEN TOPIC
Algorithm efficiency is measured in terms of time and space—that is, how fast it
runs and how much memory it uses.
The key considerations for assessing efficiency are:
Number of Steps (Big O Notation)
Number of Conditions
Number of Repetitions
2.3.1 Number of Steps (Big O Notation)
When discussing efficiency, we focus on how an algorithm's performance is
affected as the input size (n) increases. Big O Notation is a mathematical
method used to describe how the running time or memory usage grows as the
input size increases.
1. Constant Time - O(1)
The execution time remains constant regardless of the input size. Whether the dataset has
10 elements or 10 million, the operation takes the same time.
Example: Accessing the first element of an array (arr[0]).
2. Linear Time - O(n)
The execution time increases proportionally with the input size. If the input doubles, the
time doubles.
Example: Linear search in an unsorted list (checking every item one by one).
Page 10

##P32
Big O Notation (Continued)
3. Logarithmic Time - O(log n)
The execution time increases very slowly as the input grows. The algorithm repeatedly
reduces the problem size by half, making it highly efficient for massive datasets.
Example: Binary search on a sorted list.
4. Quadratic Time - O(n²)
The execution time increases proportionally to the square of the input size. Commonly
occurs with nested loops. Highly inefficient for large datasets.
Example: Bubble Sort or comparing every item in a list against every other item.

2.3.2 Number of Conditions
Conditions (IF statements) represent decision points. Excessive conditional branching
reduces performance.
Computational Cost: Every condition forces the CPU to evaluate true/false.
Nested Conditions: IF inside IF indicates a brute-force approach, reducing readability and
processing speed.
Short-Circuiting (Optimization Goal): Terminate evaluation as soon as the result is found
(e.g., using logical AND/OR optimally) rather than checking every branch.

2.3.4 The Efficiency Evaluation Framework
To evaluate an algorithm at a conceptual level, consider three fundamental
questions:
1. Does it scale? If input size grows 10x, does the running time jump 10x (linear) or 100x
(quadratic)? Quadratic scaling fails for large datasets.
2. What is the bottleneck? Focus on the most time-consuming section (usually the
deepest loop). Try to optimize that specific part.
3. Is the cost worth it? A theoretically faster O(log n) algorithm might be too complex to
code and maintain. For a list of just 50 items, a simple O(n) linear search is practically
better due to its simplicity.

2.4 Refinements to improve clarity
Improving an algorithm involves reviewing it step by step—simplifying logic,
removing redundant work, and picking smart data structures. A clear algorithm
is easier to follow.
i) Use Meaningful Names
Replace vague variables with descriptive ones.
Bad: a = b / c
Good: average = totalSum / totalItems
ii) Break into Modules
Instead of a massive block of logic, divide the process into separate, manageable
functions. (e.g., separating the CalculateSum() function from the main printing logic).
iii) Improve Structure & Indentation
Proper visual formatting reduces the mental effort needed to read the code. Deeply
packed loops and IF statements become confusing without proper spacing.
iv) Add Comments
Keep comments short and meaningful. Explain why something is done, not just what is
happening, especially for tricky logic sections.
Page 13

##P35
2.4.2 Refinements to improve Efficiency
i) Reduce Unnecessary Steps
Eliminate redundant operations. For example, in Bubble Sort, after the first pass, the largest
value settles at the end. The algorithm should be optimized to ignore that sorted portion in
the next pass, shrinking the inner loop and saving operations.
ii) Use Better Algorithms
Pick the algorithm that fits the situation. If you need to search a list of 1 million sorted
records, replacing Linear Search with Binary Search changes execution time from seconds
to milliseconds.
iii) Avoid Re-computing Values
If a calculation results in a fixed value that won't change, do not calculate it inside a loop.
Compute it once, store it in a variable, and reuse it (Memoization/Caching).
# BAD: Re-computing C repeatedly
For i = 1 to N
C = A + B
Print C * i
End For
# GOOD: Compute C once outside
C = A + B
For i = 1 to N
Print C * i
End For
iv) Use Appropriate Data Structures
Choosing the right data structure (Array, Linked List, Tree) is like picking the right tool for a
job. If you need direct access, use an Array. If data is hierarchical, use a Tree. Do not force
one structure everywhere.

2.5 Concept of Data Structure
★ GOLDEN TOPIC
A data structure is a systematic way of organizing, storing, and managing data
to enable efficient access, modification, and processing within an algorithm.
💡 Real-Life Analogy
Books on a shelf are arranged in a specific order, making it easier to locate a
particular book quickly. Files in folders are grouped systematically. Data
structures do the same thing inside computer memory.
Broad Classifications:
1. Linear Data Structures
Elements are arranged in a strict
sequence, one after the other. Each
element (except first/last) has exactly
one predecessor and one successor.
Examples: Array, Linked List, Stack,
Queue.
2. Non-Linear Data Structures
Elements are connected in hierarchical
or interconnected network ways. An
element can be connected to multiple
other elements simultaneously.
Examples: Tree, Graph.

2.6 Identify data structures in problem scenarios
To select an appropriate data structure, understand how the data is organized.
If each item has a clear "before and after" relationship, it is a linear structure. If it
branches out or connects to multiple items, it is non-linear.
2.6.1 Linear Data Structure Scenarios
i) Storing Student Grades for a Class
Structure: Array
An array is used because we usually know how many students are in the class, and all
grades are the same data type. It offers rapid lookup using indices.
ii) Music Playlist / Browser History
Structure: Linked List
Every song knows what comes after it. When one song finishes, it follows the pointer to the
next without searching. Great for frequent insertions/deletions.
iii) Undo or Redo Functionality
Structure: Stack (LIFO)
Every time a user types or formats text, it is added to the top of the stack. Pressing "Undo"
removes the most recent action first.
iv) Printer Task Scheduling
Structure: Queue (FIFO)
Documents must be printed in the exact order they were received. First-come, first-served.

2.7 Trace data retrieval in Array, List and Queue
Tracing data retrieval means following the step-by-step path of how an
algorithm finds or accesses data. Even though Array, Linked List, and Queue are
all linear, the effort to find an item is very different based on internal
organization.
2.7.1 Retrieval in Array
Every element has a fixed index (0 to n-1) pointing directly to a specific spot in memory.
The algorithm does not "search" if it knows the index; it jumps directly there (Direct
Access).

2.7.2 Retrieval in Linked List
Linked lists do not have index-based access. The only way to find something is by
starting at the Head and following the links one node at a time (Sequential Access).
Linked List: [12] -> [98] -> [23] -> [87] -> [56] -> NULL
Search Key: 87
Step 1: Check Node 1 (12). 12 != 87. Move Next.
Step 2: Check Node 2 (98). 98 != 87. Move Next.
Step 3: Check Node 3 (23). 23 != 87. Move Next.
Step 4: Check Node 4 (87). 87 == 87. FOUND! Output: True.

Summary of Chapter 2
Correctness: An algorithm is correct if its output matches expected results.
Tested using Trace Tables (manual dry runs) or Stepwise Reasoning (logic
verification).
Clarity: Easy to read, understand, and modify. Key aspects are Modularity (Single
Responsibility Principle) and Readability (Naming conventions, formatting).
Efficiency: Measured in Time (speed) and Space (memory).
Big O Notation: Describes performance scaling. O(1) is constant, O(log n) is
logarithmic (excellent), O(n) is linear, and O(n²) is quadratic (poor, nested loops).
Refinements: Improve clarity by using meaningful names and modules. Improve
efficiency by reducing redundant steps and avoiding re-computing
(memoization).
Linear Data Structures: Data follows a sequence. Arrays (fast direct access via
index), Linked Lists (nodes linked sequentially, good for insertion), Stacks (LIFO,
undo feature), Queues (FIFO, printer tasks).
Non-Linear Data Structures: Data connects hierarchically or randomly. Trees
(Parent-child hierarchy like org charts), Graphs (Network of nodes and edges like
GPS maps).
Tracing Retrieval: Arrays jump directly to an index. Linked lists traverse
sequentially from the Head. Queues remove data strictly from the Front.
