2.1 Analyze algorithms for correctness

An algorithm is correct if its output matches the expected results for a given input. Analysing correctness means showing that the algorithm produces the intended output for all valid inputs, not just one lucky example.

Two methods are used in this course:

Trace tables→paper execution, line by line→Stepwise reasoning→logic blocks, overall state

You already met the idea of a dry run in Class XI. Here you learn to do it formally, and to choose the method that fits the size of the algorithm.

Worked example: what “correct” means. An algorithm is supposed to count how many of the heights 1.91, 2.01, 1.87, 1.57, 1.48 lie between 1.57 m and 1.91 m inclusive.

Expected output: 3 (1.91, 1.87 and 1.57 qualify; 2.01 is too tall; 1.48 is too short).

If a program prints 4, it runs but it is not correct. Correctness is about the right answer, not about “no crash”.

Remember: runs ≠ correct. A logical error still produces output — just the wrong output. That is why we analyse correctness on paper before we trust the code.

Mistake: testing only one “normal” input and calling the algorithm correct.

Fix: also try edge cases (empty list, N = 0, the exact boundary values 1.57 and 1.91). The definition says all valid inputs.

2.1.1 Trace Tables ★ Golden

A trace table is a technique used to monitor how the values of variables change during the execution of an algorithm. It is a paper execution of the code — a manual walkthrough, also called a dry run. You act as the computer and fill in one row after another.

Purpose of trace tables

  • Dry running: execute the algorithm line by line by hand.
  • Debugging: find logical errors where the algorithm runs but the output is wrong.
  • Validation: check that the algorithm does what it is intended to do.

Components of a trace table

  • Line / step number — which line is being executed.
  • Variables — one column for every variable.
  • Input / output — user inputs and printed results.
  • Condition check — True/False for IF, WHILE, FOR, and similar tests.

Worked example: soldiers who meet the height rule. To qualify for training, a soldier’s height must be between 1.57 and 1.91 metres, inclusive.

Inputs: all soldiers’ heights. Output: the count of eligible soldiers.

Step 6:     SET Total = Total + 1

2.1.2 Stepwise Reasoning

Stepwise reasoning (also called logic verification) breaks an algorithm into logical sections and checks the state of the algorithm at each stage. A state is a snapshot of what is true about the variables at that moment (for example, “Sum currently holds the total of the numbers seen so far”).

You do not fill a row for every line. You think through the logic:

  1. Analyse each step of the algorithm.
  2. Check: does it start in a valid state?
  3. Does it handle all possible cases?
  4. Are the conditions correct?
  5. If the loop is correct at the start of an iteration, does it remain correct at the end?

Worked example: sum of the numbers from 1 to N.

Step 1: Start
Step 2: Input N
Step 3: SET Sum = 0
Step 4: For i = 1 to N
Step 5:   Sum = Sum + i
Step 6: END For
Step 7: Print Sum
Step 8: End

Stepwise reasoning breakdown

Final stateWhen the loop ends, Sum holds 1+2+…+N, which is the required total.
Edge case N = 0The loop body never runs, Sum stays 0. Correct (the sum of no numbers is 0).

Answers: 1. Logic verification. 2. Because no numbers have been added yet, so the running total should be zero. 3. The loop does not run and Sum remains 0, which is the correct sum of no numbers.

2.1.3 Comparing Trace Tables and Stepwise Reasoning ★ Golden

Both methods verify correctness, but they fit different situations depending on the complexity and length of the algorithm.

FeatureTrace tableStepwise reasoning
Best forSmall algorithm blocks, complex loops, and beginners learning to track variables.Large systems, architectural logic, and abstract mathematical proofs.
Effort requiredHigh. Very tedious and impractical if a loop runs 1,000 times.Moderate. Needs strong logical deduction and abstract thinking.
Primary goalCatching syntax misinterpretations or specific arithmetic errors line by line.Catching conceptual or structural flaws in the overall design.
LevelMicro-level (line by line). Checks exact values.Macro-level (logic blocks). Checks overall state.

Worked example: which method would you pick?

  1. A 12-line loop that adds five heights. Use a trace table. The loop is short, you are a beginner, and you need the exact Total.
  2. A billing system with 40 functions. Use stepwise reasoning. You cannot fill 10,000 rows. You check each module’s start state, end state and edge cases.
  3. A loop from i = 1 to 1,000 that should produce Sum = 500500. Do not write 1,000 rows. Argue: “Sum starts at 0; each i is added once; final Sum = n(n+1)/2 = 1000×1001/2 = 500500.” That is stepwise reasoning. Then dry-run a tiny N (say 5) with a trace table if you want extra confidence.

Micro vs macro. Trace table = microscope (every cell). Stepwise reasoning = map (whole city). Beginners start with the microscope; designers need the map.

Mistake: saying one method is “better” in every question.

Fix: they have different jobs. For a short dry-run in the exam, draw the table. For “explain why the algorithm is correct for any N”, write stepwise reasoning.

2.2 Evaluating the Clarity of an Algorithm

Clarity means an algorithm is easy to read, understand and modify. In many cases, evaluating clarity is even more important than making the algorithm slightly faster. A clear algorithm is easier to maintain, debug and extend over time.

The two key aspects of clarity are:

Clarity→Modularity (parts)→Readability (text and flow)

Worked example: speed versus clarity. Algorithm A finds the class average in 8 confusing lines with variables a, b, c. Algorithm B uses two named functions and takes the same number of additions. Both are O(n). Algorithm B is the better school solution because the next person (or you, in three months) can change it without breaking it.

Ask two questions: “Can I split this into parts?” (modularity) and “Can another student read it aloud and understand it?” (readability).

Mistake: treating a clever one-line trick as “better” than a clear five-line solution.

Fix: the source says clarity is often more important than speed. Board answers should praise meaningful names and modules, not compacted code.

2.2.1 Modularity

Modularity means breaking an algorithm into smaller, independent parts such as functions, classes or modules. This makes the algorithm more organised and easier to work with.

How to evaluate modularity

  1. Single Responsibility Principle (SRP). Each module should focus on one specific task. If a function calculates a sum, prints a report and saves a file, it violates SRP.
  2. Coupling. Modules should be reusable in different contexts. Good modularity means loose coupling: a change in one part does not smash the others. Tight coupling is when two functions share so many hidden details that you cannot reuse one without the other.
  3. Abstraction. A well-designed algorithm hides complex implementation details. You can call a sorting function without knowing whether it uses Bubble Sort or Selection Sort inside.

Worked example: average of an array.

Poor modularity (monoblock)

All logic sits in one block, so you cannot reuse the sum.

Step 1: Start
Step 2: Set A = [1, 2, 3, 4, 5]
Step 3: Set n = 5
Step 4: Set total = 0
Step 5: Set avg = 0
Step 6: For I = 1 to n
Step 7:   total = total + A[I]
Step 8: End For
Step 9: avg = total / n
Step 10: Print avg
Step 11: End

Good modularity (functions)

Two clear functions: CalculateSum() and FindAverage().

Step 1: Start
Step 2: Set A = [1, 2, 3, 4, 5]
Step 3: Set n = 5
Step 4: Print FindAverage(A, n)
Step 5: End

Function FindAverage(A, n)
  Sum = CalculateSum(A, n)
  Avg = Sum / n
  Return Avg
End Function

Function CalculateSum(A, n)
  Set Total = 0
  For I = 1 to n
    Total = Total + A[I]
  End For

End Function

SRP check: CalculateSum only adds; FindAverage only divides. Loose coupling: you can reuse CalculateSum to find a total without computing an average. Abstraction: the main algorithm just calls FindAverage and does not see the loop.

The source pseudocode numbers array positions from 1. Python numbers them from 0, so the loop is for i in range(n).

def calculate_sum(A, n):
    total = 0
    for i in range(n):
        total = total + A[i]
    return total

def find_average(A, n):
    return calculate_sum(A, n) / n

3.0

SRP in one line: one function, one job. If you cannot name the function with a short verb-phrase (CalculateSum, FindAverage), it is doing too much.

Mistake: copying the 1-based loop for I = 1 to n: total = total + A[I] into Python. Then A[1] skips the first item and A[5] crashes.

Fix: in Python use for i in range(n) so the indices are 0, 1, 2, 3, 4.

2.2.2 Readability

Readability is how easily another person can understand the purpose and logic of an algorithm without running it. It is about how clear the text and the flow are.

How to evaluate readability

  1. Naming conventions — consistent rules for names. Good names make an algorithm easier to search and understand.
    Bad: v = d / t
    Good: velocity = distance / time
  2. Self-documentation — the algorithm explains itself, so you need fewer comments. Meaningful names and clean formatting make the purpose obvious.
  3. Control-flow simplicity — keep the logic straightforward. Avoid deep nesting (IF inside IF inside IF), limit extra conditions, and keep each function on one task.
  4. Consistency — one style throughout: indentation, spacing, and casing (camelCase or snake_case). Then the logic stands out instead of the mess.
Names→Self-doc→Simple flow→Consistent

Worked example: the same formula, two styles.

# Hard to read
v=d/t
if v>s:
    if t>0:
        print(v)
# Readable
velocity = distance / time
speed_limit = 20
if time > 0 and velocity > speed_limit:
    print(velocity)

The second version uses names, avoids an IF nested inside an IF, and keeps one consistent snake_case style. You can understand it without running it.

Remember readability as N-S-S-C: Names, Self-documentation, Simple flow, Consistency.

Mistake: dumping a comment on every line (total = total + 1 # add one to total).

Fix: if the name already says it, skip the comment. Comments should explain why, not repeat what.

2.3 Assess Algorithm Efficiency

Algorithm efficiency is measured in terms of time and space — how fast it runs and how much memory it uses.

The key considerations for assessing efficiency are:

  1. Number of steps (described with Big O notation).
  2. Number of conditions (IF decisions).
  3. Number of repetitions (loops).
Time (speed)+Space (memory)→Efficiency

Worked example: two ways to find a name in 1,000,000 sorted records.

Linear search checks about 1,000,000 names in the worst case (time grows with n). Binary search checks about 20 names (it halves the list each time). Both can be correct and clear. They are not equally efficient.

Efficiency is always “as the input grows”. An algorithm that feels instant on 10 items can freeze on 10 million items if it is O(n²).

Mistake: judging efficiency by how short the code looks.

Fix: a five-line nested loop can do n² work. Count steps, conditions and repetitions — not lines of text.

2.3.1 Number of Steps (Big O Notation) ★ Golden

When we discuss efficiency we ask how performance changes as the input size n increases. Big O notation is a mathematical method used to describe how the running time (or memory) grows as n grows. We ignore small constants and keep the most important term: if an algorithm does 3n + 5 steps we write O(n).

In computer science, log n almost always means log base 2 (how many times you can halve n until you reach 1).

Worked example C — O(log n): binary search on a sorted list. Each step throws away half of the remaining items. For 8 sorted numbers the worst case is about 4 comparisons (floor(log2 8)+1).

def binary_search(arr, key):
    low = 0
    high = len(arr) - 1
    steps = 0
    while low <= high:
        mid = (low + high) // 2
        steps = steps + 1
        if arr[mid] == key:
            return mid, steps
        if arr[mid] < key:
            low = mid + 1
        else:
            high = mid - 1
    return -1, steps

Key 40 is found at index 6 after 2 comparisons. Key 3 is found at index 0 after 3 comparisons. Never more than a handful of steps, even if the list later grows to a million (about 20 steps).

Worked example D — O(n log n): Merge Sort idea. To sort 8 items, Merge Sort makes log2 8 = 3 split-levels, and each level walks all 8 items once, so work ≈ 8 × 3 = 24, which matches the growth table. Bubble Sort on 8 items is on the order of 8² = 64 comparisons. That gap becomes enormous at n = 1,000,000.

Worked example E — O(n²): nested loops.

n = 4
count = 0
for i in range(n):
    for j in range(n):
        count = count + 1
print(count)
16

Inner body runs n × n = 16 times. That is the pattern of Bubble Sort and of “compare every item with every other item”.

Order from fastest to slowest (for large n): O(1) → O(log n) → O(n) → O(n log n) → O(n²).

Mnemonic: “Constant Logs Never Need Squares” — Constant, Logarithmic, N, N-log-N, Squares.

Mistake 1: writing O(n) for binary search because “there is a loop”. The loop runs about log n times, not n times.

Mistake 2: writing O(2n) or O(n+5). Big O drops constants: both are O(n).

Mistake 3: using binary search on an unsorted list. Binary search is O(log n) only on sorted data.

2.3.2 Number of Conditions

Conditions (IF statements) are decision points. Every condition forces the CPU to evaluate True or False, so excessive branching reduces performance.

  • Computational cost. Each IF is extra work, even if the rest of the algorithm is simple.
  • Nested conditions. IF inside IF often means a brute-force approach. It hurts both readability and speed.
  • Short-circuiting (the optimisation goal). Stop evaluating as soon as the result is known. In a logical AND, if the first part is False the second part is skipped. In a logical OR, if the first part is True the second part is skipped.

Worked example: cheap test first. You only divide if the denominator is not zero. Place the cheap, safe test on the left so Python never evaluates the dangerous part.

x = 0
y = 10
if x != 0 and (y / x) > 2:
    print("ratio is large")
else:
    print("skipped safely")
skipped safely

x != 0 is False, so AND short-circuits and y / x is never attempted. If you wrote the division first, the program would crash. Same idea in the soldier algorithm: a False height test skips Step 6.

Put the cheapest / most likely False test first in an AND, and the most likely True test first in an OR. That is short-circuiting used on purpose.

Mistake: writing a chain of nested IFs when one compound condition would do (as in the velocity example in 2.2.2).

Fix: flatten with AND/OR, and rely on short-circuiting instead of extra layers.

ہر IF پروسیسر سے True/False پوچھتی ہے اس لیے زیادہ شاخیں کارکردگی گھٹاتی ہیں۔ اندرونی IF اکثر brute-force ہوتی ہے۔ شارٹ سرکٹ (Short-circuit) کا مطلب ہے جیسے ہی جواب معلوم ہو جانچ روک دی جائے، مثلاً AND میں پہلی شرط False ہو تو دوسری نہ چلے۔

2.3.3 Number of Repetitions

Repetitions (loops) are the most significant factor in algorithm efficiency. The structure of the loop decides how time grows with n.

Nested loopsFor each element, process all other elements. Operations explode.Poor — O(n²)

Worked example: count the inner-body runs.

2.3.4 The Efficiency Evaluation Framework

To evaluate an algorithm at a conceptual level, ask three questions:

  1. Does it scale? If n grows 10 times, does time jump 10 times (linear) or 100 times (quadratic)? Quadratic scaling fails for large datasets.
  2. What is the bottleneck? Focus on the most time-consuming section (usually the deepest loop) and try to improve that part.
  3. Is the cost worth it? A theoretically faster O(log n) algorithm can be too complex to code and maintain. For a list of just 50 items, a simple O(n) linear search is practically better because it is simple.
Does it scale?→Where is the bottleneck?→Is the extra complexity worth it?

2.4 Refinements to improve clarity and efficiency

Improving an algorithm means reviewing it step by step: simplifying logic, removing redundant work, and picking smart data structures. A clear algorithm is easier to follow; an efficient one wastes fewer steps.

2.4.1 Refinements for clarity

  1. Use meaningful names. Replace vague variables with descriptive ones. Bad: a = b / c. Good: average = totalSum / totalItems.
  2. Break into modules. Divide a massive block into functions, for example separating CalculateSum() from the printing logic.
  3. Improve structure and indentation. Packed loops and IF statements confuse the reader. Spacing reduces mental effort.
  4. Add comments. Keep them short. Explain why something is done, not just what is happening, especially for tricky logic.

2.4.2 Refinements for efficiency

  1. Reduce unnecessary steps. In Bubble Sort, after the first pass the largest value has settled at the end. Ignore that sorted tail on the next pass by shrinking the inner loop, and you save comparisons.
  2. Use better algorithms. Searching 1 million sorted records with Binary Search instead of Linear Search changes the time from seconds to milliseconds.
  3. Avoid re-computing values (memoization / caching). If a value never changes, compute it once outside the loop, store it, and reuse it.
  4. Use appropriate data structures. Direct access → array. Hierarchical data → tree. Do not force one structure everywhere.

Worked example 1 — shrinking Bubble Sort’s inner loop (n = 5). A naive inner loop always runs n−1 = 4 times, for 4 passes: 16 comparisons. The refined inner loop runs 4, then 3, then 2, then 1: 10 comparisons.

n = 5
naive = 0
for i in range(n - 1):
    for j in range(n - 1):
        naive = naive + 1

refined = 0
for i in range(n - 1):
    for j in range(n - 1 - i):
        refined = refined + 1

print(naive, refined)
16 10

Same output, fewer additions. That is caching: compute once, reuse N times.

Clarity: N-M-I-C (Names, Modules, Indentation, Comments). Efficiency: S-A-C-D (Shrink steps, Algorithm choice, Cache, Data structure).

Mistake: “optimising” by renaming variables and thinking that is an efficiency refinement.

Fix: meaningful names improve clarity. Efficiency refinements change the amount of work (fewer loop iterations, a better algorithm, no re-compute, a better structure).

وضاحت بہتر کرنے کے لیے معنی خیز نام، ماڈیول، درست indentation اور مختصر تبصرے استعمال کریں۔ کارکردگی کے لیے فضول قدم ہٹائیں (ببل سارٹ میں ترتیب شدہ دم نظر انداز کریں)، بہتر الگورتھم چنیں (لینیئر کی جگہ بائنری سرچ)، لوپ کے اندر وہی حساب بار بار نہ کریں (Caching/Memoization)، اور مناسب ڈیٹا سٹرکچر رکھیں۔

2.5 Concept of Data Structure ★ Golden

A data structure is a systematic way of organising, storing and managing data so that an algorithm can access, modify and process it efficiently.

Real-life analogy. Books on a shelf are arranged in a set order, so you can find a title quickly. Files in folders are grouped on purpose. Data structures do the same job inside computer memory.

1. Linear data structures

Elements stand in a strict sequence, one after another. Each element (except the first and last) has exactly one predecessor and one successor.

Examples: Array, Linked List, Stack, Queue.

2. Non-linear data structures

Elements are connected in a hierarchy or a network. One element can connect to several others at the same time.

Examples: Tree, Graph.

Worked example: classify each everyday picture.

  1. Students standing in a single assembly line → linear (each has one in front and one behind).
  2. A family tree of grandparents, parents and children → non-linear (one parent, several children).
  3. Roads linking Karachi, Hyderabad, Sukkur and Larkana in many ways → non-linear (a network).

Ask: “Does each item have at most one next item?” Yes → linear. “Can one item link to many, or can links form a net?” → non-linear.

Mistake: calling a tree “linear” because you can walk it from top to bottom.

Fix: walking is traversal. The shape is hierarchical: one parent, many children. That is non-linear.

ڈیٹا سٹرکچر ڈیٹا کو منظم طریقے سے رکھنے کا نظام ہے تاکہ الگورتھم اسے جلدی استعمال کر سکے۔ لکیری ڈھانچوں میں عناصر قطار میں ہوتے ہیں (ایرے، لنکڈ لسٹ، سٹیک، کیو)۔ غیر لکیری میں ایک عنصر کئی سے جڑ سکتا ہے (ٹری، گراف)۔ الماری کی کتابیں اور فولڈرز کی مثال یاد رکھیں۔

2.5.1 Linear Data Structures: Array

An array holds a collection of similar items (the same data type) placed next to each other in contiguous memory (one continuous block).

Each item has a position number called an index, usually starting from 0. Because the address of any cell can be calculated from the index, you can jump straight to it. That is direct access (also called random access), and it is O(1).

Worked example: read by index.

A = [23, 76, 12, 90, 34, 68]
print(A[3])
print(A[0])
90
23

Index 0 is the first shelf on the row. The third item that humans call “number 4” is index 3. Formula in your head: position from the left, minus one.

Limitation. Arrays are fast to read by index but inflexible to grow in the middle. Inserting a new value between 12 and 90 means shifting 90, 34 and 68 one cell to the right. That shift is O(n), so arrays are a poor fit when you insert and delete in the middle all the time.

2. In the diagram, what is A[2]?

Answers: 1. The items sit in one continuous block, next to each other. 2. 12. 3. Later elements must all be shifted right to make room.

Linear Data Structures: Linked List

A linked list stores data as a chain. Unlike an array, the items are not one continuous block. Each separate piece is a node sitting somewhere in memory.

Each node has two parts:

  1. the actual data;
  2. a link (pointer) holding the memory address of the next node.

The first node is pointed to by HEAD. The last node’s link is NULL (nowhere). To find an item you start at HEAD and follow links one by one — sequential access, O(n).

Real-life example: browser history. Clicking Back follows the pointer to the previous page-node.

Worked example: walk from HEAD to print every data field.

nodes = [23, 76, 12, 90]
for data in nodes:
    print(data, end=" -> ")
print("NULL")
23 -> 76 -> 12 -> 90 -> NULL

There is no nodes[2] jump in a real linked list. The loop above models following each link once. Inserting a new node between 76 and 12 only means changing two pointers — you do not shift the rest of a big block, which is why lists beat arrays for frequent insert/delete.

Array = row of lockers with numbers on the doors. Linked list = treasure hunt: each clue (link) tells you where the next box is.

Mistake: writing list[3] and calling it linked-list access.

Fix: a true linked list has no index. Python’s list type is an array-like structure. In this chapter, “linked list” means HEAD-and-pointers.

Linear Data Structures: Stack ★ Golden

A stack is a linear data structure that works on the LIFO principle: Last-In, First-Out. The last element added is the first one removed. You cannot pull an item from the bottom or the middle.

2.5.2 Non-Linear Data Structures: Tree

A tree organises data in a hierarchy. Everything branches out from a single starting point called the root.

It creates a strict one-to-many (parent–child) relationship. That is an excellent way to show how roles flow in an organisation.

Real-life examples: a family tree (grandparents → parents → children) and folders inside folders on a drive.

Worked example: name the relationships.

  • Root: Principal.
  • Children of the root: Administrative Head, Academic Dean.
  • Children of Academic Dean: HOD Math, HOD CS.
  • HOD CS has one parent (Academic Dean), not two — that is the tree rule. If HOD CS also reported sideways to Accounts as an equal link, the picture would become a graph.

Tree = family / folders / organogram. One root. Branches down. Parent–child, not a web of equals.

Non-Linear Data Structures: Graph

A graph organises data when things connect in a flexible, complex way. Unlike a tree, there is no strict hierarchy: any node can connect to any other node.

  • Nodes (vertices) — the items (cities, people).
  • Edges — the connections (roads, friendships).

Examples: Facebook friends; GPS mapping (the fastest route between two cities).

Worked example: Karachi – Hyderabad – Sukkur – Larkana. Cities are vertices. Roads are edges. You can travel Karachi → Hyderabad → Sukkur or Karachi → Larkana → Sukkur. There is no single “root city”. That is a graph, and GPS uses it to pick a fast route.

Tree ⊂ Graph in shape-talk: a tree is a special graph with one root and no cycles. If you need cycles or many-to-many links, say graph.

Mistake: using a tree for GPS because “Hyderabad comes under Sindh”.

Fix: administration can be a tree; roads are a graph because you can loop and take alternative paths.

گراف لچکدار روابط کے لیے ہے: کوئی سخت درجہ بندی نہیں، کوئی بھی نوڈ کسی سے جڑ سکتا ہے۔ نوڈز (Vertices) چیزیں ہیں، کنارے (Edges) تعلق۔ فیس بک دوست اور GPS نقشہ کلاسیکی مثالیں ہیں۔ چکر (Cycle) اور کئی راستے گراف کو ٹری سے الگ کرتے ہیں۔

1. What are the two parts of a graph?

2. Give two source examples of graphs.

3. State one difference between a tree and a graph.

Answers: 1. Nodes/vertices and edges. 2. Social networks (Facebook friends) and GPS mapping. 3. A tree has a hierarchy and one root; a graph has no strict hierarchy and any node may connect to any other (cycles allowed).

2.6 Identify data structures in problem scenarios

To pick a structure, first see how the data is organised. If each item has a clear “before and after”, it is linear. If it branches or connects to many items, it is non-linear.

2.6.1 Linear scenarios

  1. Storing student grades for a class → Array. You usually know how many students there are, and all grades are the same type. Indices give rapid lookup.
  2. Music playlist / browser history → Linked list. Every song knows what comes next. When one finishes, follow the pointer. Frequent insert/delete is cheap.
  3. Undo or Redo → Stack (LIFO). Each typing or formatting action is PUSHed. Undo POPs the most recent action.
  4. Printer task scheduling → Queue (FIFO). Documents print in the exact order they were received. First-come, first-served.

2.6.2 Non-linear scenarios

  1. Organisational chart of a college → Tree. Principal is the root, then deans, then HODs, then teachers. Clear parent–child links.
  2. GPS navigation and maps → Graph. Cities are nodes, roads are edges. No strict top-down hierarchy. Several routes can reach the same destination.

Chapter 2 Review

Chapter summary

  • Correctness: output matches expected results for valid inputs. Test with a trace table (manual dry run) or stepwise reasoning (logic verification).
  • A trace table is micro-level: line, variables, I/O, conditions. Best for small loops. The soldier heights [1.91, 2.01, 1.87, 1.57, 1.48] print Total = 3.
  • Stepwise reasoning is macro-level: valid start, all cases, correct conditions, loop stays correct. Sum 1..N starts at 0; N = 0 stays 0; N = 5 becomes 15.
  • Clarity (read, understand, modify) often beats a tiny speed gain. It has two parts: modularity and readability.
  • Modularity: SRP (one job), loose coupling, abstraction (call Sort without knowing Bubble vs Selection). Split CalculateSum and FindAverage.
  • Readability: names (velocity = distance / time), self-documentation, simple flow, consistent style.
  • Efficiency = time + space. Drivers: number of steps (Big O), conditions, repetitions.
  • Big O: O(1) constant (arr[0]), O(log n) binary search, O(n) linear search, O(n log n) Merge Sort, O(n²) nested loops / Bubble Sort. Quadratic fails as n grows.
  • Framework: Does it scale? What is the bottleneck (deepest loop)? Is the extra complexity worth it? For n = 50, simple O(n) can beat fragile O(log n).
  • Refinements: meaningful names, modules, indentation, why-comments; shrink Bubble Sort’s inner loop; better algorithms; cache constants; pick the right structure.
  • Data structure: systematic organising of data. Linear (one after another): array, linked list, stack, queue. Non-linear: tree, graph.
  • Array: contiguous, index from 0, direct access O(1), shifting on mid-insert. Linked list: nodes of data+link, HEAD to NULL, sequential access.
  • Stack LIFO: PUSH/POP at TOP (Undo). Queue FIFO: ENQUEUE rear, DEQUEUE front (printer).
  • Tree: one root, parent–child (college chart). Graph: vertices + edges, no strict hierarchy (GPS, friends).
  • Five operations: insert, delete, traverse, search, sort. Choose by next/previous, parent/child, FIFO, relationships, or reverse-of-entry.
  • Retrieval: array can jump to an index; a list walks from HEAD; a queue only removes the Front.

Short questions — model answers

  1. An algorithm is correct if its output matches the expected results for a given input (and does so for all valid inputs). The two methods are trace tables and stepwise reasoning (logic verification).
  2. Components: line/step number, a column per variable, input/output, and a condition-check column. A dry run acts as the computer, so you see logical errors where the program runs but the values go wrong, and you can validate that the intention is met.
  3. Trace table: small blocks/complex loops/beginners; high effort (bad for 1,000 iterations); catches arithmetic/line mistakes; micro-level exact values. Stepwise reasoning: large systems and proofs; moderate effort; catches conceptual/structural flaws; macro-level overall state.
  4. Modularity is breaking an algorithm into smaller independent parts (functions, classes, modules). SRP: each module does one task. Coupling: modules should be loosely coupled so a change in one does not break others. Abstraction: hide inner details (call Sort without knowing Bubble vs Selection).
  5. Naming conventions, self-documentation, simple control flow, consistency of indentation/spacing/casing. Bad: v = d / t. Good: velocity = distance / time.
  6. Big O describes how time or memory grows as n grows. O(1): arr[0]; O(log n): binary search; O(n): linear search; O(n log n): Merge Sort; O(n²): Bubble Sort / nested loops.
